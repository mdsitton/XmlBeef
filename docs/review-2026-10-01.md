# XmlBeef code review

Review date: 2026-10-01. Reviewed revision:
`cb3534e19ea925da0ecaae12930ce4f712f0b4f8`.

This review covers XML reading, encoding detection, streams, the internal DTD subset,
namespace processing, document mutation, both document writers, typed mapping, and the
verification harnesses. Its purpose is to identify concrete defects and guide the next
implementation work. It records the state before fixes; recommendations are proposals.

The foundation is sound: memory and streams share one parser, names are interned, tree
operations are iterative, and the ownership model is mostly explicit. The main problems
are maintaining invariants when input buffers move or document semantics change. The
review reproduced silent corruption, invalid output, lost values, inconsistent limits,
and one process crash despite the existing verification baseline passing.

## Scope and evidence

The review started with [the plan](plan.md), [the specification reference](spec-reference.md),
[the implementation survey](implementation-survey.md), [the suite documentation](test-suites.md),
[the architecture](architecture.md), and [the status baseline](status.md). Source inspection
was followed by focused CLI inputs and temporary Beef executables outside the repository.
No parser fixes or permanent regression tests were added during the review.

Evidence is distinguished throughout:

- **Reproduced:** the primary failure was observed in both Linux Debug and Release.
- **Source inspection:** an additional consequence or opportunity follows from the code,
  but was not separately reproduced or measured.
- **Proposed:** a design, fix, test, or feature recommendation requiring implementation.

Code references identify the relevant symbol and its line at the reviewed revision. Line
numbers may move as fixes land. The Beef examples below are statements for a helper
returning `Result<void, XmlParseError>`, with `using System;` and `using XmlBeef;`, unless
they include a type declaration. `Try!` propagates setup failures. A caller should inspect
the resulting output or error as described. Appendix A supplies executable CLI
reproductions for the parser findings without depending on temporary files.

Priority meanings:

- **P1:** fix first because the reproduced behavior corrupts data, terminates a process,
  or directly makes ordinary document operations emit malformed XML.
- **P2:** correctness or API contract defects that need fixing, with narrower triggers
  or a design decision to settle first.
- **P3:** improvements to maintainability, scalability, or performance; measured benefits
  remain to be established where indicated.

These priorities express recommended implementation order, not security exploit ratings.

## R01 Public identifiers become stale during stream reads

**Evidence:** reproduced in Debug and Release, including the document and event stream
paths. **Location:** [XmlReaderCore.Dtd.bf](../src/XmlBeef/XmlReaderCore.Dtd.bf#L279),
`ReadExternalId`, especially the public-literal result at line 293 and system-literal
read at line 301. Also relevant:
[XmlReaderCore.bf](../src/XmlBeef/XmlReaderCore.bf#L681), `RebaseViews`.

### Trigger and observed result

Construct the input as a comment containing 123 `z` characters followed by:

```xml
<!DOCTYPE r [<!NOTATION n PUBLIC "PUBLIC_IDENTIFIER" "SYSTEM_TEXT">]><r/>
```

Replace `SYSTEM_TEXT` with 200 `s` characters and read through a 16-byte stream buffer.
The suite form from memory contains:

```xml
<!NOTATION n PUBLIC 'PUBLIC_IDENTIFIER' 'ssss...'>
```

The streamed suite form contains:

```xml
<!NOTATION n PUBLIC 'sssssssssssssssss' 'ssss...'>
```

Both reads succeed. The literal values above describe the result; the omitted system
text is not part of the runnable input. Appendix A creates the exact input.

### Cause and impact

`ReadPubidLiteral` returns a view into the current window. `ReadExternalId` then keeps
that view while calling whitespace and system-literal scanning helpers that can refill
or move the window. The local/out-parameter view is not among the fields that
`RebaseViews` updates. Its old address can now refer to another part of the input.

This violates the core's stated rule that locals hold offsets across reads. It silently
changes the document's data. The observed failure is corruption after movement; this
review does not establish an exploit or claim a reproduced use-after-free. The helper
is shared by DOCTYPE, external ENTITY, and NOTATION identifiers, so its callers need an
audit even though the visible reproduction uses a notation.

### Proposed fix and regression coverage

Store the public literal's start and length, then construct its view after the last
operation that can refill. An alternative is to copy the identifier before reading
further, but offsets fit the parser's allocation strategy. Audit the returned system
view too: a caller must not keep it across another refill without owning or relocating it.

Test both identifiers through DOCTYPE, ENTITY, and NOTATION declarations. Include a
preceding construct that causes dropped bytes, buffer sizes 16 and 64 KiB, long
whitespace between literals, and literals spanning a refill. Compare actual public and
system identifiers as well as canonical output. A process completing successfully is
not sufficient evidence for this defect.

## R02 Dictionary updates crash when a value element is missing

**Evidence:** reproduced in Debug and Release; both processes exited on signal 5,
`SIGTRAP`. **Locations:** [XmlMap.bf](../src/XmlBeef/XmlMap.bf#L118),
`XmlMapEntries.Enumerator.GetNext`; the `XmlMapWriter` constructor at line 226 and
`Finish` at line 305.

### Trigger and observed result

```beef
let doc = scope XmlDocument();
Try!(doc.Read("<r><entry><key>a</key></entry></r>"));
let writer = scope XmlMapWriter(
    doc.Root, .KeyValueElements, "entry", "key", "value", "", default);
writer.Finish();
```

The XML parser accepts the document. The entry enumerator intentionally supports
missing values, marking such an entry with `mHasValue = false`. Calling `Finish()` on
the writer nevertheless terminates the process.

### Cause and impact

For this shape, `mElement` is set to the value element only when one exists. A missing
value leaves it as the default invalid handle. The writer checks `found.Check()` but
does not account for `mHasValue`, then indexes the invalid node. `Finish()` passes the
saved node to removal helpers, which require a valid handle.

Generated reading already skips entries with no value. Updating a document should not
turn this supported representation into a fatal programming error. The problem also
affects how a writer finds an existing entry when it later needs to add the missing value.

### Proposed fix and regression coverage

Keep the entry element's identity separately from the value location. A dictionary
entry exists even if its value is absent. That identity lets the writer either complete
it or remove it safely. Simply skipping the entry in the index can leave duplicates
behind when a value for its key is subsequently written.

Test a missing value with an empty dictionary update, a supplied replacement value,
duplicate keys where one occurrence lacks a value, and an object value. Assert that
the update completes without a trap and produces the intended entry set. Verify
through generated `XmlWrite` as well as the runtime writer.

## R03 Text escaping does not handle adjacent node boundaries

**Evidence:** reproduced in Debug and Release. **Location:**
[XmlDocument.Write.bf](../src/XmlBeef/XmlDocument.Write.bf#L436), `AppendTextEscaped`;
`WriteLeaf` invokes it separately for each text node.

### Trigger and observed result

```beef
let doc = scope XmlDocument();
Try!(doc.Read("<r/>"));
doc.Root.AddText("]]");
doc.Root.AddText(">");
let written = scope String();
doc.Write(written);
```

Output:

```xml
<r>]]></r>
```

Rereading fails at line 1, column 4 with the error that `]]>` is not allowed in text.
Each individual value passed to the mutation API is valid text.

### Cause and impact

The escaping helper examines the two preceding bytes in the current `StringView`.
It cannot see the brackets emitted for a preceding sibling. The parsed document usually
merges adjacent text, which explains why ordinary parse/write tests miss this case;
mutation can create separate text nodes.

This is an output well-formedness defect independent of namespace or DTD processing.
XML's character-data rule forbids the resulting sequence; see
[XML 1.0 character data](https://www.w3.org/TR/REC-xml/#syntax).

### Proposed fix and regression coverage

Carry the last two characters of emitted character data across sibling writes, or
consider the already-written output when deciding whether to escape `>`. Escaping every
`>` would also be correct, but changes the stated minimal-escaping behavior. The same
rule must work when PreserveStyle combines copied source with generated text.

Test splits `"]]" + ">"`, `"]" + "]>"`, and `"]" + "]" + ">"`; removing markup
between existing text nodes; and adding generated text after a preserved source slice.
Assert successful rereading and equal aggregate text.

## R04 Encoding detection ignores declarations beyond 4096 bytes

**Evidence:** reproduced in Debug and Release through memory and streams, documents
and events. **Locations:** [XmlEncodingDetector.bf](../src/XmlBeef/XmlEncodingDetector.bf#L208),
`Prepare`, `cPrefixBytes = 4096`, and `DeclaredEncoding` at line 268;
[XmlStreamCursor.bf](../src/XmlBeef/XmlStreamCursor.bf#L117), `Begin`.

### Trigger and observed result

Start the declaration with `<?xml version="1.0"`, insert 4,100 spaces, then append one
of these suffixes:

```xml
encoding="ISO-8859-1"?><r>é</r>
encoding="US-ASCII"?><r>é</r>
```

Encode the first complete input as Latin-1 and the second as UTF-8. The first is rejected
as invalid UTF-8. The second is accepted, despite containing bytes outside the declared
ASCII encoding. Both declarations are subsequently accepted by the declaration parser.

### Cause and impact

Preparation examines only a fixed prefix. The declaration pre-scan returns an empty
encoding name both when none is present and when the prefix ends before the name. The
reader commits to UTF-8 and never reconciles that choice with the later declaration.

This mixes absence with incomplete detection. It affects built-in encodings and can
prevent an otherwise configured custom converter from being selected. The latter is
a source-inspection consequence, not a separately reproduced converter case.

### Proposed fix and regression coverage

Use a bounded, resumable declaration probe. It should distinguish no declaration,
no encoding pseudo-attribute, a completed name, malformed syntax, and a probe that
still needs input. A configured declaration-length limit can reject excessively long
declarations explicitly; it should not silently change the selected encoding. Memory
and stream preparation should use the same rule.

Test whitespace before `encoding`, around `=`, and before its quote; names and closing
quotes crossing the detection boundary; wide encodings; unsupported names; converters;
and contradictory declarations. Include exact-limit and one-byte-over cases. Preserve
the intentional UTF-8 BOM policy recorded in the plan.

## R05 Entity frames do not restore the retention coordinate

**Evidence:** reproduced in Debug and Release with a 16-byte event stream.
**Locations:** [XmlReaderCore.bf](../src/XmlBeef/XmlReaderCore.bf#L559), `PushFrame`,
`PopFrame` at line 593, and `Grow` at line 660;
[XmlReaderCore.Text.bf](../src/XmlBeef/XmlReaderCore.Text.bf#L73), `ReadText` after a pop.

### Trigger and observed result

Build the document in this order:

1. A comment containing 20,000 `x` characters.
2. `<!DOCTYPE r [<!ENTITY e "<c/>text">]>`.
3. `<r>&e;`, followed by 9,990,000 `t` characters, then `</r>`.

With the default limits, reading events from memory succeeds. Streaming the same
bytes through a 16-byte buffer fails with:

```text
1:10000005: A construct is longer than MaxTokenBytes (10000000)
```

The long text construct is below 10,000,000 bytes. Replacing the entity's value with
plain `text` makes the streamed control case pass.

### Cause and impact

An event beginning inside the entity sets `mRetain` in that entity's offset space.
`PopFrame` restores `mData`, `mBase`, `mPos`, and `mEnd`, but not retention. Text then
continues into the document, and `Grow` passes the small entity-relative value to the
stream cursor as though it were a document offset.

The token budget consequently includes unrelated earlier document bytes. It can also
make the cursor retain more than the current construct needs. The demonstrated error
is a false rejection; other effects of that invalid retention coordinate were not
exhaustively characterized.

### Proposed fix and regression coverage

Treat retention as part of the saved input context, and ensure it is restored or
recomputed correctly when a scan continues after a frame ends. Saving one field is
only sufficient if it also represents the construct currently in progress. Check
nested frames and attribute expansion before choosing the exact representation.

After correcting the coordinate, shrink the regression by using a small configured
`MaxTokenBytes`: keep each construct below the limit while making cumulative document
offsets exceed it. Cover entities with markup followed by text, nested entities, pops
near refills, and memory/stream parity. Do not address this by simply raising the limit.

## R06 Entity amplification uses different denominators

**Evidence:** reproduced in Debug and Release through 16-byte and 64 KiB event streams.
**Locations:** [XmlReaderCore.bf](../src/XmlBeef/XmlReaderCore.bf#L611), `CountExpansion`;
[XmlStreamCursor.bf](../src/XmlBeef/XmlStreamCursor.bf#L412), `InputBytes`; and
[XmlCursor.bf](../src/XmlBeef/XmlCursor.bf), the memory cursor's input-size property.

### Trigger and observed result

Declare `e0` as 1,500 `a` characters, then declare `e1`, `e2`, and `e3` as ten
references to the preceding entity. Read `&e3;` inside `<r>`, close the root, and append
a comment containing 2,000,000 `t` characters.

The expanded character data is 1,500,000 bytes. The whole input is about 2 MB. Memory
reading succeeds; both stream buffer sizes fail near the reference with an error naming
`MaxEntityAmplification (10)`.

### Cause and impact

The shared check divides expansion work by `mCursor.InputBytes`. The memory cursor
reports the complete input size. The stream cursor reports bytes read so far, which
depends on read-ahead and buffer size. Trailing input is included in one denominator
but not yet in the other.

The reproduced stream rejection can be a defensible policy for untrusted prefixes,
but it contradicts the advertised consistency between input paths. The memory policy
also allows trailing padding to dilute the ratio. A non-seekable stream cannot know
the final size before it reaches the end.

### Proposed fix and regression coverage

Define what the ratio measures: expansion against consumed input, available input,
or complete input. A consistent consumed-input rule is a useful candidate, provided
the memory cursor reports the same relevant progress and entity-local offsets do not
replace document progress. Retain the absolute expansion limit independently.

Changing the rule may intentionally reject inputs previously accepted from memory;
document that behavior. Avoid making seekability or buffer size silently select the
policy. Test padding before and after expansion, different read chunk sizes, both
threshold boundaries, and ratios at and around the configured limit.

## R07 Whole-input conversion disables the stream token limit

**Evidence:** reproduced in Debug and Release with Windows-1252 fallback. The custom
converter shares this code path by source inspection. **Location:**
[XmlStreamCursor.bf](../src/XmlBeef/XmlStreamCursor.bf#L192), `ReadWhole`, especially
`mMaxTokenBytes = 0` at line 210.

### Trigger and observed result

Read `<r><!--`, 1,000 `x` characters, and `--></r>` with:

```beef
var config = XmlReadConfig();
config.StreamBufferBytes = 16;
config.MaxTextBytes = 0;
config.MaxTokenBytes = 100;
```

The read fails with a token-limit error. Set
`config.EncodingFallback = .Windows1252` and the same UTF-8 input succeeds.

### Cause and impact

Fallback selection requires inspecting the whole input with the current API. After
that buffering step, `ReadWhole` disables the token limit because the normal mechanism
depends on restricting the window and entering `Fill` when a construct exceeds it.
Whole-input availability does not remove the caller's limit on a construct.

The observed issue is a limit bypass under an opt-in setting. Whole-input buffering
also changes the memory behavior of stream reads. `MaxInputBytes` remains a separate
budget; this review does not claim it is bypassed.

### Proposed fix and regression coverage

Enforce construct budgets independently of how much source is already available.
Whole-input paths can still expose a limited logical window or use explicit scanner
checks. Document the buffering requirement of fallback and the converter hook, but
keep their resource settings meaningful.

Test oversized tags, comments, text, PIs, CDATA, and internal subsets with fallback
enabled on both valid UTF-8 and actual Windows-1252. Add equivalent converter tests,
exact-limit cases, and input-size checks. Do not rely solely on one cursor's refill
behavior to enforce a public resource policy.

## R08 Namespace name checks do not cover every production

**Evidence:** the three inputs below were accepted in Debug and Release, with memory
and streams, documents and events. **Locations:**
[XmlReaderCore.Dtd.bf](../src/XmlBeef/XmlReaderCore.Dtd.bf#L466), `ReadNameGroup` and
`ReadContentModel`; [XmlReaderCore.Text.bf](../src/XmlBeef/XmlReaderCore.Text.bf#L195),
`ScanReferenceName`. `ParameterReference` needs a related audit by source inspection.

### Trigger and observed result

```xml
<!DOCTYPE r [<!ELEMENT r (a:b:c)>]><r/>
```

```xml
<!DOCTYPE r [<!ATTLIST r n NOTATION (a:b) #IMPLIED>]><r/>
```

```xml
<!DOCTYPE r SYSTEM "unused"><r>&a:b;</r>
```

All three succeed with the default namespace processing. The last uses an unread
external subset so that undeclared-entity handling does not mask the invalid name.

### Cause and impact

These paths scan XML `Name` syntax without applying the stricter namespace role.
Other declaration paths already call `CheckQName` or `CheckNoColon`, so checking is
distributed and incomplete. A declaration that will not be used still needs its syntax
checked. Skipping an entity's contents does not waive the reference's name syntax.

Element and attribute names require qualified names; the other relevant name tokens
require names without colons. These restrictions are described in
[Namespaces document conformance](https://www.w3.org/TR/xml-names/#Conformance).
They are separate from DTD validity constraints and do not require adding a validator.

### Proposed fix and regression coverage

Make the expected role explicit when scanning a name, or consistently call role-specific
helpers at every production. Apply qualified-name checks to content-model element names
and colon-free checks to notation groups and entity references. Review parameter entity
references and references retained within entity values too.

Test each affected production with an empty prefix, empty local part, extra colon,
invalid local-name start, and non-ASCII names. Verify the same XML names are allowed
where appropriate with `Namespaces = false`; ordinary enumeration `Nmtoken` handling
should not accidentally receive rules intended for notation names.

## R09 Mutations leave DTD dependencies unresolved

**Evidence:** all three failures below were reproduced in Debug and Release.
**Locations:** [XmlNode.Mutation.bf](../src/XmlBeef/XmlNode.Mutation.bf#L132), `Rename`;
[XmlDocument.Mutation.bf](../src/XmlBeef/XmlDocument.Mutation.bf#L75), `RemoveNode`;
[XmlDocument.Write.bf](../src/XmlBeef/XmlDocument.Write.bf#L230), omission of defaulted
attributes; [XmlDocument.Style.bf](../src/XmlBeef/XmlDocument.Style.bf#L264), source reuse.

### Trigger and observed result

Read:

```xml
<!DOCTYPE r [<!ATTLIST r a CDATA 'default'>]><r/>
```

`doc.Root.GetAttribute("a")` returns `default`. Rename the root to `s`, then write:

```xml
<!DOCTYPE r [<!ATTLIST r a CDATA 'default'>]>
<s/>
```

The edited document still reports `a = default`; the reread document has no `a`.
Removing the DOCTYPE instead produces `<r/>` and loses the same value on reread.

For a second case, read with `MetadataMode = .PreserveStyle`:

```xml
<!DOCTYPE r [<!ENTITY e 'text'>]><r>&e;</r>
```

Remove `doc.DocType`, then write. Output remains `<r>&e;</r>`, and rereading rejects
the undeclared entity. The in-memory text had already been expanded successfully.

### Cause and impact

Defaulted flags tell the writer to omit attributes because declarations will restore
them. Rename changes the name used to select those declarations; DOCTYPE removal removes
them altogether. Neither operation updates that assumption.

Preserved entity references similarly depend on declarations outside the represented
subtree. Dirty marking follows structural ancestors, but removing the DOCTYPE is not
a structural ancestor change to the root's text. The source slice remains clean even
though its meaning is no longer available.

The DOCTYPE/root-name mismatch after rename is not itself the non-validating parser
defect being reported. The defect is loss of attributes the mutation API retained.

### Proposed fix and regression coverage

Define mutation semantics for DTD-dependent values. Under the existing promise that
rename retains attributes, promote affected defaults to specified attributes when their
old declarations no longer apply. Removing the DTD should materialize defaults and
regenerate dependent entity-derived source. Alternatively, restrict unsupported DTD
operations explicitly; silent loss is not an adequate contract.

Check defaulted namespace declarations, existing tokenized attribute types, skipped
external entities, and newly applicable defaults on the renamed element. These are
follow-up cases, not separately demonstrated failures in this review. Test both writers
and compare normalized attributes and aggregate text directly. A syntax-only reread
would miss the lost-default cases.

## R10 Carriage returns in generated CDATA are normalized away

**Evidence:** reproduced in Debug and Release both through mutation and through parsed
entity replacement text. **Location:**
[XmlDocument.Write.bf](../src/XmlBeef/XmlDocument.Write.bf#L251), the CDATA branch of `WriteLeaf`.

### Trigger and observed result

```beef
let doc = scope XmlDocument();
Try!(doc.Read("<r/>"));
doc.Root.AddCData("\r");
let written = scope String();
doc.Write(written);
```

After rereading `written`, the content character is 10 rather than 13.

The same loss is reachable from this accepted input without any API mutation:

```xml
<!DOCTYPE r [<!ENTITY e "<![CDATA[&#13;]]>">]><r>&e;</r>
```

Its direct suite form is `<r>&#13;</r>`. The CLI `-rewrite` path produces
`<r>&#10;</r>`.

### Cause and impact

The CDATA writer handles `]]>` but emits CR literally. The reader preserves the CR
introduced into entity replacement text by a character reference. Once the writer
places that character directly in a new document, ordinary line-end processing changes
it to LF. See [XML end-of-line handling](https://www.w3.org/TR/REC-xml/#sec-line-ends).

This loses character content even though both parses succeed. The text writer already
escapes CR, so CDATA is inconsistent with that semantic preservation behavior.

### Proposed fix and regression coverage

Close the CDATA section around CR, emit `&#13;` as character data, and reopen it as
needed. The resulting parse can contain both text and CDATA nodes; the preserved
requirement here is the character sequence, not identical section boundaries.

Test lone CR, CRLF, repeated CR, CR near `]]>`, and CR adjacent to an unencodable
character handled by `WriteBytes`. Cover canonical output and regenerated PreserveStyle
pieces. Comments and PI data containing generated CR warrant a related audit, but they
cannot use the same character-reference solution; this report does not claim that
case is solved by the CDATA fix.

## R11 Document mutations do not enforce namespace well formedness

**Evidence:** unbound-prefix and duplicate-expanded-name output was reproduced in Debug
and Release. Other invalid binding operations follow from source inspection.
**Locations:** [XmlNode.Mutation.bf](../src/XmlBeef/XmlNode.Mutation.bf#L185),
`SetAttribute`, plus `AddElement`, `Rename`, moves, and namespace removal;
[XmlDocument.Mutation.bf](../src/XmlBeef/XmlDocument.Mutation.bf#L155), namespace recomputation.

### Trigger and observed result

```beef
let doc = scope XmlDocument();
Try!(doc.Read("<r/>"));
doc.Root.SetAttribute("p:a", "v");
```

Writing succeeds and produces `<r p:a="v"/>`. Rereading reports an unbound prefix.

For another case:

```beef
Try!(doc.Read("<r xmlns:p='urn:x' xmlns:q='urn:x' p:a='1'/>"));
doc.Root.SetAttribute("q:a", "2");
```

The writer emits both attributes. Rereading rejects their identical namespace and
local-name pair.

### Cause and impact

Mutation checks lexical name and character validity, then recomputes namespace IDs.
The recomputation is not validation: an unbound prefix becomes `None`, and it does not
detect duplicate expanded names or enforce reserved binding rules.

This leaves a gap between the mutation documentation's well-formed-output intent and
what writing actually guarantees. It also means a document's stored namespace identity
can disagree with what a successful XML consumer would be allowed to interpret.

### Proposed fix and regression coverage

Choose a clear construction policy. Rejecting every incomplete intermediate state
would break useful sequences that add an element and then declare its namespace. One
option is to allow construction temporarily, expose `Validate` or a checked writer
returning `Result`, and validate before file output. Another is transactional namespace
mutation. The exact API is a design choice, not an existing feature.

Share the reader's namespace rules with the mutation validator. Test unbound names,
removal of a used binding, reserved `xml` and `xmlns` cases, prefix undeclaration,
duplicate expanded names after rebinding, and moves between scopes. Respect the current
documented move behavior that resolves names at their destination; do not silently
replace it with a policy that preserves the old namespace by inventing declarations.

## R12 Typed writing does not recognize the implicit xml binding

**Evidence:** reproduced in Debug and Release through the public binding runtime used
by generated attribute writers. **Location:**
[XmlBind.bf](../src/XmlBeef/XmlBind.bf#L739), `FindPrefix`, called by `SetAttribute`.

### Trigger and observed result

```beef
let doc = scope XmlDocument();
Try!(doc.Read("<r/>"));
XmlBind.SetAttribute(doc.Root, "lang",
    "http://www.w3.org/XML/1998/namespace", "en");
```

Output:

```xml
<r xmlns:ns0="http://www.w3.org/XML/1998/namespace" ns0:lang="en"/>
```

Rereading rejects the `ns0` binding.

### Cause and impact

The mutation lookup recognizes the predefined binding, but `FindPrefix` searches
explicit `xmlns` attributes for a matching prefix. Without an explicit declaration,
it reports no match, and the attribute writer allocates `ns0`.

The XML namespace is already bound to `xml`; other prefixes cannot bind to it. See
[reserved prefixes and namespace names](https://www.w3.org/TR/xml-names/#xmlReserved).
This affects ordinary typed fields such as `xml:lang` and `xml:space`.

### Proposed fix and regression coverage

Return `xml` immediately for the XML namespace and ensure reserved namespaces never
reach the ordinary prefix-allocation path. Use a shared binding rule so explicit
declarations are not required for a predefined namespace.

Test `xml:lang` and `xml:space` without explicit declarations, with one present, and
on descendants. Verify a generated `[XmlName(..., Namespace = ...)]` field, not just
the runtime helper. Validate behavior for attempts to map the XMLNS namespace too.

## R13 Strict typed claims discard namespace identity

**Evidence:** the strict-reading failure was reproduced in Debug and Release. The
generator collision limitation is established by source inspection.
**Locations:** [XmlBind.bf](../src/XmlBeef/XmlBind.bf#L999), `CheckStrict`;
[XmlSerializerCodeGen.bf](../src/XmlBeef/XmlSerializerCodeGen.bf#L447), `ScanChain`,
especially claim lookup at line 542.

### Trigger and observed result

```beef
[XmlObject(Name = "r", Strict = true)]
class StrictModel
{
    [XmlName("a", Namespace = "urn:expected")]
    public String value ~ delete _;
}
```

Read the following into a new model:

```xml
<r xmlns:p='urn:other' p:a='x'/>
```

`XmlSerializer.Read` returns `.Ok`, while `value` remains null. The attribute did not
match the field, but strict processing treated it as mapped.

### Cause and impact

Field lookup uses namespace identity. Strict checking uses only a list of local names.
The two definitions of a mapped field disagree. The same list is also used by catch-all
dispatch. `ScanChain` stores claims by name alone, so distinct namespaces with the same
local name are treated as collisions by the inspected generator code.

Strict mode consequently misses content it promises to reject. Namespace-rich formats
also cannot express some otherwise nonconflicting mappings under the current claim
representation.

### Proposed fix and regression coverage

Represent claims as namespace and local-name pairs, together with any intended wildcard
policy. Preserve the existing documented behavior that an empty namespace matches any
namespace for element binding but only no namespace for attribute binding. A simple
pair type without that distinction would change API semantics.

Use the same claim definition for field lookup, strict checks, aliases, collision
detection, inheritance, and catch-all lists/maps. Test an expected namespace, a different
namespace with the same local name, no namespace, two explicit namespace mappings with
the same local name, and an inherited mapping. Add a compile-time fixture for the
collision case before treating that additional consequence as independently verified.

## R14 Views and stale handles do not follow one validity contract

**Evidence:** both related failures were reproduced in Debug and Release.
**Locations:** [XmlNode.bf](../src/XmlBeef/XmlNode.bf#L413), `XmlAttribute`;
[XmlDocument.Mutation.bf](../src/XmlBeef/XmlDocument.Mutation.bf#L238), attribute removal;
[XmlNode.Mutation.bf](../src/XmlBeef/XmlNode.Mutation.bf#L360), `CheckContainer`.

### Attribute identity changes

```beef
let doc = scope XmlDocument();
Try!(doc.Read("<r a='1' b='2'/>"));
let saved = doc.Root.Attributes[0];
doc.Root.RemoveAttribute("a");
// saved.Name is now "b", and saved.Value is "2".
Try!(doc.Read("<r other='3'/>"));
// saved.Name is now "other", and saved.Value is "3".
```

An attribute stores only its document and absolute table index. Removing an attribute
shifts later records into that slot. Clearing or rereading has no generation check
inside the saved attribute. Moving another element's attribute span during growth
also leaves old views pointing to obsolete records by source inspection.

The documented view lifetime lasts until clear/read, so silent identity changes during
mutation conflict with that promise. After clear/read, the caller is using an invalid
view, but the library's checked-handle model should detect it rather than exposing a
different attribute. This is not a demonstrated use-after-free.

### A stale document node still accepts mutations

```beef
Try!(doc.Read("<r/>"));
let savedDocumentNode = doc.DocumentNode;
doc.Clear();
savedDocumentNode.AddElement("unexpected");
// savedDocumentNode.IsValid is false, but doc.Root.Name is "unexpected".
```

`CheckContainer` explicitly exempts handles whose document is non-null and ID is zero
from its failed-validity check. That bypasses generation validation for the document node.

### Proposed fix and regression coverage

Choose an attribute-view contract. Stable identities can use owner plus an attribute
ID and checked generation; invalidating views on mutation can use document/owner
revision checks and explicit documentation. Recomputing an index from the owner/name
alone still needs to distinguish a removed attribute from a later replacement.

Remove the document-node exemption from generation validation while keeping freshly
obtained `DocumentNode` handles usable on an empty document. Test removal of the viewed
attribute and preceding attributes, span relocation, remove/re-add, Clear, Read, and
node removal. Test stale document-node operations after both Clear and Read. Expected
fatal misuse cases must be isolated in a subprocess or a suitable fatal-error harness;
they should not make the ordinary test process crash.

## Performance and memory findings

The following recommendations preserve the existing fast-path approach. No elapsed-time
comparison was collected: the machine's load average was about 5, above the repository's
quiet-machine threshold of roughly 2. These opportunities are not measured speedups.

### P01 Expanded attribute duplicate checking remains quadratic

**Evidence:** source inspection. **Location:**
[XmlReaderCore.Tags.bf](../src/XmlBeef/XmlReaderCore.Tags.bf#L518), the second duplicate
check in `ResolveNamespaces`.

Qualified-name duplicate checking already switches to a set above 16 attributes. The
expanded-name check always compares earlier prefixed attributes pairwise. With 4,000
prefixed attributes, its inner loops can inspect 7,998,000 pairs. One prefix declaration
is sufficient to reach this workload, so the namespace-binding limit does not prevent it.

Use pairwise comparison for small counts and a reusable set of `(namespace ID, local ID)`
above a measured threshold. This retains the simple common path and improves large-tag
behavior. Apply the set after namespace resolution so aliases to the same URI still
collide. Preserve diagnostic choice and source position when reporting a duplicate.

Measure small SVG tags and synthetic tags at 16, 17, 64, 512, and thousands of attributes,
including late duplicates. Use instruction counts where appropriate, then timing on a
quiet machine. Review `ApplyDeclarations` separately: its per-declaration linear search
through attributes is another source-inspection candidate for large DTD workloads, but
this review did not benchmark that path.

### P02 Word scans do not resume after refills

**Evidence:** source inspection. **Locations:**
[XmlReaderCore.Text.bf](../src/XmlBeef/XmlReaderCore.Text.bf#L25), `ScanText`;
[XmlReaderCore.Tags.bf](../src/XmlBeef/XmlReaderCore.Tags.bf), `ReadAttributeValue`.

`ScanText` runs its eight-byte loop before entering a scalar loop. When the scalar
loop grows the input window, it stays scalar; it does not return to scanning words in
the new window. A large streamed text run therefore uses the word path mainly on its
initial window. The attribute-value scanner has a similar opportunity. Comments,
CDATA, and PI scanning are also primarily scalar in the inspected code.

Organize scans as a resumable word loop plus a boundary/tail loop. After a refill, resume
at the current offset rather than the construct start. Maintain validated-window and
retention invariants, and do not retain raw local pointers across `Grow`.

Profile long text and attribute values at realistic stream buffer sizes, both plain
and containing references or CR. Check that improvements do not add overhead to small
in-memory SVGs, read beyond the valid window, or introduce repeated rescanning. Further
vectorization should follow profiles; the existing word scans already fit the design.

### P03 Text budgets are enforced after substantial work

**Evidence:** reproduced in Debug and Release for decoded text; broader scanner exposure
is based on source inspection. **Location:**
[XmlReaderCore.Text.bf](../src/XmlBeef/XmlReaderCore.Text.bf#L163), `TextEvent`, called
after `ReadText` has assembled the buffer.

With `MaxTextBytes = 16` and a 16-byte stream buffer, reading `<r>`, 100,000 `&amp;`
references, and `</r>` consumed all 500,007 bytes before returning the limit error.
The decoded text has 100,000 characters. The configured value limit therefore bounds
the accepted result but does not closely bound the work or temporary allocation before
rejection. Other input and token limits remain independently relevant.

Check decoded size before or during appends, including runs, numeric references,
predefined references, entity text, and attribute whitespace. Some scanners already
check plain attribute runs incrementally, but the whitespace/reference branches need
a consistent policy. Entity values, comments, CDATA, and PIs should be reviewed too.

Keep zero-copy plain text cheap: check scanned lengths at refill or run boundaries,
and guard decoded appends at their natural boundaries rather than adding a branch to
every ordinary byte. Test exact limits and long runs of only references or whitespace.
A counting stream or allocator can prove early failure; allow bounded detection and
read-ahead overhead, so a test should not demand exactly 16 source bytes read.

### P04 Long-lived documents accumulate retained storage

**Evidence:** source inspection; retained-memory growth during long edit sequences was
not measured. **Locations:** [XmlTextArena.bf](../src/XmlBeef/XmlTextArena.bf#L39),
`NextChunk` and `Reset`; [XmlDocumentStore.bf](../src/XmlBeef/XmlDocumentStore.bf),
`NewText`; [XmlDocument.Mutation.bf](../src/XmlBeef/XmlDocument.Mutation.bf#L216),
attribute span movement.

Arenas retain their chunks across resets deliberately. Mutation allocates replacement
values without reclaiming the old bytes, and attribute growth can copy spans to the
table's end, leaving holes. Removed nodes likewise keep their slots until clear. This
is compatible with stable views and bulk cleanup, but memory can reflect cumulative
editing history rather than the size of the current live document.

This is a storage-lifecycle concern, not a LeakSanitizer leak finding. Object destruction
can still free everything. Parser reuse benefits from retaining capacity, so making
every Clear free it would sacrifice an intentional optimization.

Consider an explicit compaction or memory-release operation and document its effect on
handles and borrowed text. A separate release-capacity operation may be useful after an
unusually large parse. Measure repeated value replacement, alternating attribute edits
on different elements, node removal, and large-to-small reads. Compare live content,
retained allocation, and resident memory separately; allocator behavior affects the last.

## Architecture and readability recommendations

### A01 Make input context and offset ownership explicit

The generic core and separate cursors should be retained. They prevent duplicate XML
implementations and allow the memory cursor's refill checks to fold away. The issue is
the implicit coordination of `mData`, `mBase`, `mPos`, `mEnd`, `mRetain`, entity depth,
and event source coordinates.

R01 and R05 are concrete examples of that coordination failing. A source offset, an
entity offset, and a buffer address can have the same primitive type while having
different lifetimes and meanings. The existing comments explain the invariants well,
but each helper still has to remember them manually.

An internal input-context representation or narrowly scoped helpers should make frame
save/restore complete and distinguish ranges from borrowed views. Use offsets while
scanning and construct views only after operations that can refill. Audit both normal
parsing and collect-errors recovery, which also unwinds frames and relocates state.

Keep this change focused: new allocations, per-byte virtual dispatch, or abstraction
layers that obscure the fast paths would undermine the current strengths. Compare
instruction counts after the correctness fixes and retain Debug checks at boundaries
where they can validate the representation without burdening every scanned byte.

### A02 Separate structural dirtiness from semantic dependencies

PreserveStyle tracks changed nodes and ancestors, which works for local value and
layout edits. XML also has dependencies outside a subtree: DTD defaults, entity
declarations, and namespace bindings. R09 and R11 show why ancestry alone cannot
establish whether a source slice remains safe to emit.

Define the logical document invariants and the validation policy first. Then make
mutation operations invalidate their semantic dependents as well as their layout.
Conservative regeneration on rare DTD edits may be preferable to building a large
dependency graph. More selective dependency tracking can follow if editor workloads
show a need.

The canonical and preserving writers should share well-formedness decisions and
escaping rules. Their output formats differ, but generated text, namespaces, and
defaulted-value decisions must agree. Checking final output by reparsing is valuable
in tests; a production validation API should operate on document state rather than
requiring a second full parse of every write.

### A03 Make generated serializer code easier to inspect

[XmlSerializerCodeGen.bf](../src/XmlBeef/XmlSerializerCodeGen.bf) has 1,494 lines at the
reviewed revision. Much of its complexity is necessary: roles, lists, dictionaries,
aliases, inheritance, converters, and allocation policy. Dense `AppendF` emission with
embedded source and indentation makes its consequences harder to inspect than the
runtime parser methods.

`FieldPlan` already separates some planning from emission. Extend that boundary into
cohesive planning/claim-validation and emission components, with shared namespace-aware
claim data. Make generated source available for debugging or compile-fixture inspection,
subject to the Beef compiler's supported mechanisms.

Use focused compile fixtures for representative roles, collisions, and inheritance.
Use behavior and ownership tests for emitted code, especially failure midway through
owned lists or maps. Source snapshots can aid diagnosis, but avoid treating whitespace
changes in generated code as correctness regressions. R13 should be fixed through the
shared claim representation before cosmetic file splitting.

### A04 Document lifetime contracts consistently

The distinction between owned `String` storage and borrowed `StringView` is generally
well expressed. R14 shows that identity-bearing views need more than a storage address.
Define which operations invalidate nodes, attributes, lists, iterators, and returned
text, and enforce the chosen contract through one set of generation/revision rules.

[XmlParseError](../src/XmlBeef/XmlError.bf) has a deliberately short message lifetime:
its text views thread-local buffers overwritten by the next error on that thread.
This is documented, and is not presented here as a new verified bug. It still deserves
clear examples for callers collecting diagnostics or using multiple readers. `Detach`
copies into those buffers; it does not make an indefinitely owned diagnostic. The
document's collected errors follow a different lifetime because their text is copied
into its store.

Prefer explicit copying examples or an owned diagnostic helper if applications need
durable errors. Any such API must preserve Beef's cleanup requirements and should not
add allocations to successful event reads.

## Missing features and scope choices

These are capabilities to prioritize when their use cases arise, not evidence of
nonconformance. Existing scope decisions in the plan remain the reference.

### F01 Public element skipping and subtree reading

The reader exposes pull events, but does not yet provide the documented future
`ReadSubtree` capability or a public element-skipping convenience. The recovery helper
named `SkipElement` is internal and is not that API.

These operations would help applications skim large files and build one record at a
time. Define whether a helper begins on `StartElement`, where it leaves the reader,
how an empty element behaves, and what it does after an error. Skipping must still check
well-formedness and apply resource limits. Subtree documents need to preserve the
namespace bindings required by their copied content, including bindings declared on
ancestors outside the subtree.

### F02 Streaming output

Current document output and `WriteFile` assemble the output in memory. A streaming
writer would allow generation without a full document and reduce output buffering for
large files. Its state machine needs shared escaping, namespace policy, and error
handling; R03 is particularly relevant to chunked text writes.

This should be introduced after the current writer's invariants are fixed so it does
not create a third divergent implementation. PreserveStyle is a separate use case
because it already keeps original source and edit metadata.

### F03 Typed deserialization without a complete document

[XmlSerializer.Read](../src/XmlBeef/XmlSerializer.bf#L22) creates a document and raises
metadata to Positions before filling the object. That supports located errors and
reuse of the document binding API, but typed input is not currently a direct event-to-
object path. A Stream-backed document still grows with the complete document.

Subtree reading is a useful first step for typed record processing. A later event-based
mapping API would need its own choices about unknown content, converters, lists,
lookahead, and location storage. Measure the actual model and allocation cost before
replacing the existing convenient document-based API.

### F04 External resolution remains an opt-in future feature

An external entity/subset resolver is planned as needed. Its absence is consistent
with the current safe default of opening nothing external. If introduced, keep
resolution explicit, retain expansion/input budgets, define source locations and base
URIs, and test unresolved entities. Network fetching should not become a default.

### F05 Validation and query languages remain outside the stated scope

DTD/XSD validation, XML 1.1 semantics, XInclude, XPath, and XSLT are not implementation
omissions under the current plan. Fixing R08 does not require DTD validation; fixing
R11 concerns namespace well-formedness of produced documents. Avoid broadening the
project into those features as a substitute for correcting the current contracts.

### Mutation coverage is deliberately restricted

combinations relevant to each invariant rather than making every regression an

explicit tests, not left to chance in byte-mutation fuzzing.

Fatal misuse tests need a controlled subprocess result. Confirming a desired assertion
failure with `ShouldFail` does not make an uncontrolled signal acceptable in the main
Beef test process.

## Suggested implementation order

1. Fix the independent, directly observed failures R01, R02, and R03 with focused

2. Correct input policy R04 through R08. Decide the amplification denominator before
   changing it, and keep token limits independent of whole-input conversion.

4. Make typed claims namespace-aware for R13, including collisions and catch-all

5. Apply incremental text-budget enforcement, then profile the duplicate-check and

under `AGENTS.md`. Run Windows Debug and TestRelease verification before committing

## Appendix B Resource limit reproduction

These complete methods demonstrate R07 and P03. They need `using System.IO;` in addition
to the namespaces noted above. Use `Main` to call `Limits()` in a small executable that
depends on XmlBeef, and build/run it in both Debug and Release.

```beef
static void ReadWithBudget(StringView label, StringView input, XmlReadConfig config)
{
    let stream = scope FixedMemoryStream(.((uint8*)input.Ptr, input.Length));
    let reader = scope XmlReader();
    reader.Reset(stream, config);
    while (true)
    {
        switch (reader.Next())
        {
        case .Ok(let event):
            if (event == .EndOfDocument)
            {
                Console.WriteLine("{} accepted {} bytes", label, stream.Position);
                return;
            }
        case .Err(let error):
            Console.WriteLine("{} failed after {} of {} bytes: {}", label,
                stream.Position, input.Length, error.ToString(.. scope .()));
            return;
        }
    }
}

static void Limits()
{
    let input = scope String("<r>");
    for (int i < 100000)
        input.Append("&amp;");
    input.Append("</r>");

    var config = XmlReadConfig();
    config.MaxTextBytes = 16;
    config.StreamBufferBytes = 16;
    ReadWithBudget("MaxTextBytes=16", input, config);

    input.Set("<r><!--");
    for (int i < 1000)
        input.Append('x');
    input.Append("--></r>");
    config.MaxTextBytes = 0;
    config.MaxTokenBytes = 100;
    ReadWithBudget("MaxTokenBytes=100", input, config);

    config.EncodingFallback = .Windows1252;
    ReadWithBudget("MaxTokenBytes=100 with fallback", input, config);
}
```

The reviewed builds report that the text-budget read consumes all 500,007 bytes before
failing. The comment fails its token budget without fallback and succeeds with it.
The 1,014-byte comment input fits the initial detection prefix, so its stream position
alone is not evidence about early token-budget rejection; the accept/reject difference
is the relevant observation for R07.

| P02 | Measured first (`bench/instructions.sh` gained `stream` and `stream4k` columns): reading from a `Stream` cost 2–5× the in-memory event pass, and most of it was not the scans but line counting (every start tag's position, a column per code point byte by byte, and the bytes a refill drops counted a second time). The counter now goes 8 bytes at a time and `Fill` continues the located count; the text, attribute-value, comment, PI and CDATA scans resume their words after a refill, and a start tag's inline value scan hands its position on. Streams then cost 1.2–1.5× memory input; memory input itself improved slightly (svg-generated 8.6 to 7.9 instructions per byte). A follow-up (SP1) located only the elements still open when the buffer moves, instead of every start tag, and counts newlines alone (columns on demand, words without a byte below 0x0E skipped two at a time): streams now cost 1.1–1.3× memory input. A stream test compares word-counted positions with a byte-by-byte count over random mixes of multi-byte characters and line ends. |
